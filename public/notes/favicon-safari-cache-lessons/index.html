一次 favicon 排障的完整复盘：Safari 缓存锁死

主页标签页的网站图标，在 Chrome 里正常、在 Safari 的其它子页面里也正常，唯独 Safari 的主页一直是默认的灰底字母占位。为这一个图标，排查历经十余轮、横跨文件名、域名、声明顺序、图标设计等多个方向，最终定位为 Safari 27 的独立 favicon 数据库按 URL 锁死——根因不在网站，而在浏览器的缓存机制。本文完整还原过程、根因，以及这趟弯路里真正值钱的那些教训。

00 / 结论

一句话先说清

问题与答案都各只有一句
现象：同一个图标文件，Chrome 主页正常、Safari 子页面正常、Safari 带参数的 URL（?test=xxx）也正常，唯独 Safari 的裸主页 hilltoken.net 显示默认灰底白字占位。

根因：Safari 把每个网站的 favicon 存在一个独立的数据库 ~/Library/Safari/Favicon Cache/ 里，按「完整 URL」做缓存键。主页这个裸 URL 在某次图标改动中，被 Safari 记成了一个「加载失败 → 永远显示默认占位」的死状态，之后就不再重新请求。而这个数据库不受「清除历史记录 / 网站数据」影响，只能手动删目录重建。
一句话教训：favicon「某页有、某页没有」时，先让出问题的页面与正常页面做一次对照实验（带参数 URL vs 裸 URL），这一招比盲目改代码、改缓存、改域名高效一个量级。
01 / 现象

问题长什么样

四个看似矛盾的事实

最初看起来只是一件小事：主页标签页的图标不见了。但随着排查深入，暴露出来的现象组合越来越"不合逻辑"，这也是它难查的根本原因——每条事实单独看都说得通，合在一起却互相打架：

浏览器主页 hilltoken.net子页面 /notes/…
Chrome✓ 正常图标✓ 正常图标
Safari✗ 灰底白字占位✓ 正常图标

更关键的是第三个事实：在 Safari 里访问一个带查询参数的 URL（https://hilltoken.net/?test=xxx），图标又正常了。这三个事实叠加——同一份代码、同一个文件，Chrome 正常、Safari 子页正常、Safari 带参数正常，唯独 Safari 裸主页不行——其实已经把答案锁死了：问题不在网站，而在 Safari 对「裸主页」这一个特定 URL 的缓存状态。

为什么绕了这么久：真正的原因不是"太难"，而是排查的前半段一直假设"网站哪里写错了"，于是不断在代码、文件、域名上找差异；而后半段又假设"缓存锁死但能被清掉"，于是让用户反复清缓存。两个假设都对了一半，却都漏了关键一环——Safari 的 favicon 缓存是一个独立的、按 URL 锁定的、且普通清缓存碰不到的系统数据库。
03 / 根因

Safari 到底是怎么把图标"锁死"的

三层缓存，只清了一层

Safari 对网站图标维护了至少两套彼此独立的缓存，这恰恰是"清了缓存也没用"的根源：

缓存路径作用普通清缓存能清掉吗
网站数据Safari → 设置 → 隐私 → 管理网站数据Cookie、localStorage、网页缓存能
历史记录Safari → 历史记录 → 清除历史记录浏览历史、部分缓存能
favicon 数据库~/Library/Safari/Favicon Cache/标签页 / 地址栏的小图标不能，需手动删目录

favicon 数据库的关键特性是按「完整 URL」做缓存键。也就是说，在 Safari 眼里，下面这些是三个不同的缓存条目：

  • https://hilltoken.net（无尾斜杠）——被锁死，显示灰底占位
  • https://hilltoken.net/?test=xxx（带参数）——正常，因为它是"另一个 URL"
  • https://hilltoken.net/notes/…（子路径）——正常，同样因为 URL 不同

当主页图标在排查过程中反复改动（浅灰、朱砂红、透明底、换文件名……），Safari 在某个时刻把裸主页这个 URL 记成了「加载失败 → 默认占位」，之后就再也不去服务器重新请求了。这不是网站的 bug，是 Safari 的缓存 bug——同样的代码和文件，Chrome 能正常显示，就是最硬的证据。

为什么 agent 无法代你清：这个目录受 macOS 的 TCC 隐私保护，任何程序（包括有自动化权限的助手）都无法读写或删除它。这是系统级的故意设计，只能由用户本人在「访达」里手动删除。这也是排查拖到最后一刻才解决的技术性原因之一。
04 / 解法

正确且唯一的清除方法

三步，亲测有效
  1. 完全退出 Safari：不是关标签页，是 ⌘Q 彻底退出，确认 Dock 图标下的小圆点消失。
  2. 删除 favicon 缓存目录：在访达按 ⌘⇧G 打开「前往文件夹」，输入 ~/Library/Safari/Favicon Cache 回车，全选内容 ⌘Delete 移入废纸篓并清空。若旁边还有 Touch Icons Cache（收藏 / 起始页的大图标缓存），一并删除。
  3. 重开 Safari：首次打开时图标可能短暂是灰的，Safari 会重新去服务器拉取，几秒后即恢复。
若连 ~/Library/Safari 都进不去（提示无权限），先到「系统设置 → 隐私与安全性 → 完全磁盘访问权限」，把「访达」或「终端」加进去，再回来删除。
05 / 复盘

这趟弯路里真正值钱的五条

下次遇到同类问题的第一反应
  1. 先做对照实验，再动手改。favicon「某页有、某页没有」，第一时间让出问题页面和正常页面各测一次：换浏览器、换带参数的 URL、换子路径。三者的差异能直接区分「网站问题」还是「客户端缓存问题」，比盲改代码高效一个量级。
  2. 标准答案先去看官方的「网站图标」定义。图标该长什么样，往往品牌规范里写得清清楚楚（本站就在品牌素材页的「网站图标」卡片里）。不要自己重新设计图标——这次中途把图标改成"朱砂红山形""透明底"，都是因为没先看标准答案。
  3. 别假设"缓存锁死"就乱改文件名 / 域名 / 声明顺序。这些改动各自都是正确的，但都不是根因，反而引入了新的不一致（比如两套文件名分裂）。先找到"正常页 vs 异常页"的真实差异，再决定改什么。
  4. 记住 Safari 的 favicon 是独立数据库。清"网站数据 / 历史记录"对它无效；它按 URL 锁定、受 TCC 保护、程序无法代清。这是本次排查最核心、也最反直觉的一个知识点。
  5. 别过度依赖"看截图猜图标"。视觉模型描述小图标时反复矛盾（一会儿"灰底H"、一会儿"黑底白字"）。遇到图标外观问题，直接读 SVG 源码里的 fill 颜色，比让模型"看图说话"准确得多。
06 / 沉淀

排查中的哪些操作该留、哪些该清

避免"为了修 bug 又引入新债"

为排除问题，这一路动了不少东西。事后盘点，它们分三类：

该保留的（正确且有益）

操作为什么保留
Cloudflare 配 www → apex 301统一主域名是 SEO 最佳实践，顺手消除了"双域名分裂缓存"的隐患
代码层域名统一与 301 配套，让全站 canonical 指向 hilltoken.net
favicon 统一官方米纸底设计回到品牌规范的标准答案
favicon 声明移到 head 最前规范写法，避免被压缩 HTML 影响解析
两套图标文件字节级统一消除根目录 / 品牌套的文件分裂隐患

该清理的（过程中的"垃圾"）

操作处理
site-icon.*（5 个文件）已删——"换新文件名"的错误尝试产物，无引用
hilltoken-icon-2026.* 等旧图标已删——更早的旧命名，无引用
_headers 里的死规则已删——对应文件删掉后，这些规则成了死配置
编辑器临时备份文件已删——index.html + 随机后缀的垃圾文件，会被误部署
特别说明 Cloudflare 那条 301 规则：建议永久保留，不要删。它不只是 favicon 问题的辅助修复，更是"www 与 apex 二选一"这个域名规范的长期正确做法——保留它，既让 SEO 更干净，也避免以后再次出现双域名缓存的坑。
07 / 结语

把一次 bug 变成一份资产

写下来的意义

一个标签页图标的消失，本来只是件芝麻大的事。但它逼着我们把浏览器缓存机制、域名规范、图标规范、以及"如何高效排查一个跨层的怪问题"完整走了一遍。这些经验如果不写下来，下次还会在同样的坑里再绕十几圈；写下来，它就从一次"浪费时间"变成一份可复用的资产。

这也正是这个网站想做的事情之一：把踩过的坑、得到的教训，沉淀成一份既给自己、也能给人和 Agent 读的事实源。
