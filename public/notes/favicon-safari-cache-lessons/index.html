Safari 网站图标异常：一份可复用的排查手册

标签页的网站图标（favicon）「某一页有、某一页没有」，是前端最常见也最容易被误判的怪问题之一。这份手册不记录我们当时绕了多少弯路，只沉淀三样东西：一张能定位根因的判断树、一个三步就能解决的清除方法、一份可直接照做的清单——下次你或同事再遇到，照着走即可，无需重走一遍。

00 / 结论

一句话先说清

现象 · 根因 · 解法，各一行
现象
同一个图标文件，Chrome 主页正常、Safari 子页面正常、Safari 带参数的 URL 也正常，唯独 Safari 的裸主页 hilltoken.net 显示默认灰底白字占位。
根因
不是网站的 bug。Safari 把 favicon 存在一个独立数据库 ~/Library/Safari/Favicon Cache/，按「完整 URL」做缓存键。裸主页这个 URL 在某次图标改动中被记成「加载失败 → 永远显示默认占位」的死状态，之后不再重新请求。
解法
这个数据库不受「清除历史记录 / 网站数据」影响，只能手动删目录重建：完全退出 Safari → 删除 ~/Library/Safari/Favicon Cache/ → 重开 Safari。
核心心法：favicon「某页有、某页没有」时，先让出问题的页面与正常页面做一次对照实验（带参数 URL vs 裸 URL、换浏览器）。这一招能在一分钟内区分「网站问题」还是「客户端缓存问题」，比盲目改代码、改缓存、改域名高效一个量级。

一张决策树，定位根因

照着走，最多四步出结论

这一步为什么关键：③ 的「带参数 URL 正常、裸 URL 异常」是本次排查的一锤定音证据——它证明同一份代码、同一个文件没有问题，Safari 只是把「裸主页」这一个 URL 的缓存状态锁死了。把这一步做在前面，能省掉后面十几轮无效折腾。
02 / 为什么

清缓存为什么没用

三层缓存，普通清理只碰得到前两层

Safari 对网站图标维护了至少三套彼此独立的缓存。「清除历史记录 / 网站数据」只清得到前两层，而那层真正管标签页小图标的，恰恰清不到——这就是「清了无数次也没用」的根本原因：

缓存路径 / 入口作用普通清缓存能清掉吗
网站数据设置 → 隐私 → 管理网站数据Cookie、localStorage、网页缓存能
历史记录历史记录 → 清除历史记录浏览历史、部分缓存能
favicon 数据库~/Library/Safari/Favicon Cache/标签页 / 地址栏的小图标不能，需手动删目录
Touch Icons Cache~/Library/Safari/Touch Icons Cache/收藏 / 起始页的大图标不能，需手动删目录

favicon 数据库的关键特性是按「完整 URL」做缓存键。在 Safari 眼里，下面这些是三个不同的缓存条目：

https://hilltoken.net            ← 被锁死，显示灰底占位
https://hilltoken.net/?x=1       ← 正常（另一个 URL）
https://hilltoken.net/notes/…    ← 正常（另一个 URL）
为什么程序无法代你清：这个目录受 macOS 的 TCC 隐私保护，任何程序（包括有自动化权限的助手）都无法读写或删除它。这是系统级的故意设计，只能由用户本人在「访达」里手动删除——这也是这类问题往往要拖到最后才解决的技术性原因之一。
03 / 怎么做

三步解法

亲测有效，约 2 分钟
  1. 完全退出 Safari：不是关标签页，是按 ⌘Q 彻底退出，确认 Dock 图标下的小圆点消失。
  2. 删除 favicon 缓存目录：在访达按 ⌘⇧G 打开「前往文件夹」，输入 ~/Library/Safari/Favicon Cache 回车，全选内容 ⌘Delete 移入废纸篓并清空。若旁边还有 Touch Icons Cache（收藏 / 起始页大图标），一并删除。
  3. 重开 Safari：首次打开时图标可能短暂是灰的，Safari 会重新去服务器拉取，几秒后即恢复。
若连 ~/Library/Safari 都进不去（提示无权限），先到「系统设置 → 隐私与安全性 → 完全磁盘访问权限」，把「访达」或「终端」加进去，再回来删除。
04 / 别再犯

五条避坑清单

这些动作都对，但都不是解药

下面五件事，我们当时都做过，每一件都「正确但无用」，甚至引入了新问题。列在这里，是提醒你别在它们身上再耗时间：

  • 反复改 ?v= 版本号、写 JS 动态改 href。Safari 的 favicon 缓存不按查询参数区分，改版本号对它无效。
  • 乱换文件名想「绕开旧缓存」。方向反了：Safari 对「已缓存过的老文件名」是正常的，对全新文件名反而要重新判定，还制造了文件分裂。
  • 反复清「网站数据 / 历史记录」。碰不到 favicon 那个独立数据库，白清。
  • 自己重新设计图标（改颜色、换透明底）。标准答案在品牌页的「网站图标」卡片里，先看定义，别动手改。
  • 靠「看截图猜颜色」判断图标。视觉模型描述小图标时反复矛盾。要判断图标外观，直接读 SVG 源码里的 fill 颜色值。

机器可读摘要

结构化字段，供 Agent 直接检索

为了让未来的自己、同事或任何一个 AI 助手能直接命中结论、无需通读全文，这里把关键事实抽成结构化字段。检索到「favicon / Safari / 图标某页有某页没有 / 灰底占位」时，优先返回本块：

症状
标签页图标某页有、某页没有；Chrome 正常、Safari 子页正常，唯 Safari 裸主页显示默认灰底白字占位。
根因
Safari 独立 favicon 数据库按「完整 URL」缓存锁死；裸主页 URL 被记为「加载失败 → 默认占位」。
数据库路径
~/Library/Safari/Favicon Cache/（收藏大图标另见 Touch Icons Cache/）
触发条件
排查过程中反复改动图标文件，Safari 将某一 URL 记为失败态。
解法
完全退出 Safari → 删 ~/Library/Safari/Favicon Cache/ → 重开。
程序能否代做
不能。目录受 macOS TCC 保护，须用户本人在访达手动删除。
对照实验法
带参数 URL（?x=1）正常、裸 URL 异常 → 锁定为 Safari 按 URL 缓存锁死，非网站问题。
关键词
favicon、Safari、缓存锁死、灰底占位、Favicon Cache、TCC、按 URL 缓存键、某页有某页没有。
留一句给未来的 Agent：若有人报「Safari 某页图标显示灰底字母、其它页面正常」，不要先去改网站代码或文件。先让对方做一次「带参数 URL vs 裸 URL」的对照实验确认，再指导其删除 ~/Library/Safari/Favicon Cache/。这个数据库普通清缓存碰不到，且程序无法代删。
06 / 盘点

排查中动过的操作，该留还是该清

避免「为修 bug 又引入新债」

为排除问题，这一路动了不少东西。事后盘点分两类——有益的要留，过程垃圾要清：

该保留的（正确且有益）

操作为什么保留
Cloudflare 配 www → apex 301统一主域名是 SEO 最佳实践，顺带消除了「双域名分裂缓存」的隐患
代码层域名统一与 301 配套，让全站 canonical 指向 hilltoken.net
favicon 回到官方米纸底设计回到品牌规范的标准答案
favicon 声明移到 head 最前规范写法，避免被压缩 HTML 影响解析
两套图标文件字节级统一消除根目录 / 品牌套的文件分裂隐患

该清理的（过程垃圾）

操作处理
site-icon.*（5 个文件）已删——「换新文件名」的错误尝试产物，无引用
hilltoken-icon-2026.* 等旧图标已删——更早的旧命名，无引用
_headers 里的死规则已删——对应文件删掉后成了死配置
编辑器临时备份文件已删——index.html + 随机后缀的垃圾，会被误部署
Cloudflare 那条 301 规则：建议永久保留，不要删。它不只是 favicon 问题的辅助动作，更是「www 与 apex 二选一」这个域名规范的长期正确做法——保留它，SEO 更干净，也避免以后再次出现双域名缓存的坑。
